# Using Lightweight Formal Methods to Validate a Key-Value Storage Node in Amazon S3
SOSP'21 · James Bornholt, Rajeev Joshi, Vytautas Astrauskas, Brendan Cully, Bernhard Kragl, Seth Markle, Kyle Sauri, Drew Schleit, Grant Slatton, Serdar Tasiran, Jacob Van Geffen, Andrew Warfield / AWS, UT Austin, ETH Zurich, U. Washington · https://doi.org/10.1145/3477132.3483540
Paper type: verification / validation methodology in industry (experience paper)

## Dissection
- Background: ShardStore is S3's new storage node: a key-value store (keys are shard IDs, values are shard data) on one disk. It is an LSM tree with values stored outside the tree, on append-only extents, with background reclamation (garbage collection) and LSM compaction. It gets crash consistency from soft updates: writes go to disk in a dependency order, with no journal. A run-time `Dependency` type builds the order graph; every extent append takes and returns one, and `is_persistent()` tells whether an operation reached disk. The code is 44,048 lines of Rust, highly concurrent, changes all the time, is deployed continuously, and already holds hundreds of PB in a gradual rollout.
- Problem: The team wants to check deep properties: functional correctness of API calls, crash consistency of on-disk structures, and correctness of concurrent API calls and background tasks. The checks must keep working while the code and even the spec change, and they must be maintained by engineers with no formal-methods background after the experts leave. Full verification is too costly at this size and rate of change. Ordinary tests miss the bugs that matter.
- Challenges: (1) Proof-based verification costs 3–10× the code (VeriBetrKV: 7 lines of proof per line of code). (2) A spec written by experts in a modeling language (Alloy, SPIN, Yggdrasil-style Python, which the authors used at first) is a second artifact that nobody on the team will keep in sync. (3) The natural check, "model and implementation hold the same key-value map after every call", is too strong: a crash may legally lose recent writes, and concurrent calls overlap, so there is no "after every call". (4) The crash states are too many to list at block level, and exhaustive interleaving search does not scale: a small end-to-end test has tens of thousands of atomic steps, the largest over a million. (5) Random testing only reaches states the harness can reach, and a failing random run is too long to debug.
- Solution:
  1. Insight: specs go stale when only experts touch them. Engineers already must update unit-test mocks when they change code. → Design: for each component, write a reference model in Rust with the same interface but a trivial implementation (the LSM-tree index's model is a hash map; the models total 450 lines, 1% of the code). Use it as the mock in unit tests. → The spec is updated as part of normal work, or the build breaks.
  2. Insight: you do not need to imagine scenarios. Generate them, and let the model be the oracle. → Design: property-based testing. Random sequences of operations from an alphabet (API calls plus background tasks such as reclaim and clean reboot, which are no-ops in the model) run on both model and implementation, and outputs and the key-value map are compared after each step. The implementation runs on an in-memory disk. Arguments are biased only where there is evidence (sizes near the page size). Code coverage shows blind spots. The components are deterministic, so failures shrink automatically (bug #9: 61 operations → 6). IO faults are injected with a "has failed" flag: after a fault a get may return nothing but never wrong data. → Deep bugs are found with no hand-written scenarios, and the failures can be debugged.
  3. Insight: the soft-updates code already records which writes must reach disk before others, and can say if an operation is durable. That is the crash spec. → Design: add `DirtyReboot(RebootType)` to the alphabet. The reboot type chooses per component whether it flushes, and flush operations interleaved in the sequence give partly flushed states. After a dirty reboot: if a dependency says persistent, the data must be readable (persistence). After a clean reboot: every dependency must be persistent (forward progress). → Crash bugs (a missing edge or write in the graph) are caught with no block-level enumeration and no hand-written "what may be lost" model.
  4. Insight: overlapping operations can still be checked against the sequential model by asking whether the result equals some serial order (linearizability). Exhaustive search is only affordable for small code. → Design: Loom (sound, exhaustive, for the release/acquire memory model) checks small custom concurrency primitives. Shuttle (randomized, e.g. PCT; open-sourced by the authors) checks end-to-end harnesses that Loom cannot finish. → Concurrency gets checked at every scale, and the team knowingly trades soundness for scale.
  Also: Miri for undefined behavior in unsafe Rust; Crux proves deserializers cannot panic on any input up to a size bound, plus fuzzing for larger inputs.
- Evidence: 16 issues stopped before production (5 functional, 5 crash consistency, 6 concurrency), most about data integrity, one deadlock (#12). Tens of millions of random sequences run before every deployment. Validation code: models 450 + functional 4,860 + crash 2,661 + concurrency 901 lines, about 20% of the implementation (vs. 3–10× for verified systems). Ordinary unit/integration tests: 19,540 lines. Effort: two experts full time for nine months, a third for three months. Adoption: 18% of harness lines last edited by non-experts (git blame); three engineers wrote over 100 lines each, including crash checks; four engineers wrote their own model-checking harnesses; a harness is now a standard code-review question; engineers asked to make the tests release blockers. Block-level exhaustive crash states found no extra bugs and were much slower. Biasing toward production size and get/put distributions had no effect. Known miss: one cache bug caught in code review, because tests used a cache so large the miss path never ran. Not checked: concurrent crashing executions, resource exhaustion, message parsing, request routing, business logic, parts of the control plane.

Safe background (may be explained whenever asked): LSM trees, WiscKey-style key/value separation, soft updates vs. journaling in general, write-ahead logs and fsync, append-only zones, garbage collection, mocks and unit tests (but not the idea of using the spec as the mock; that is exercise 2's answer), fuzzing, QuickCheck as a general idea, model checking and TLA+/Alloy in general, verified storage systems (FSCQ, Yggdrasil, VeriBetrKV) and their reported proof cost (3–10× the code; VeriBetrKV 7 lines of proof per line of code), linearizability, Rust's safe/unsafe split and data-race freedom.
Protected terms (not before the reveal of exercise N): "lightweight formal methods" (2), ShardStore (2), "reference model" (2), "property-based testing" (2), "refinement" (2), `Dependency` / `is_persistent` by name (2), Shuttle, Loom, DirtyReboot (2).

## Exercise 1: Problem finding — the tests pass, so what is missing?
### Brief
You work on the team building a new storage node for a large cloud object store. A node runs one key-value store per disk: keys are shard IDs, values are shard data. Data sits in chunks on append-only disk regions (extents); an LSM tree maps each shard to its chunks, and is itself stored as chunks. Background reclamation copies live chunks off an extent and resets it; LSM compaction runs at the same time. For crash consistency the node orders its disk writes (soft updates), with no journal. It is about 44,000 lines of Rust, with 19,540 lines of unit and integration tests. Changes ship continuously and the node already stores hundreds of petabytes in a gradual rollout. Leadership has lent you two formal-methods experts for nine months. None of the engineers has used a formal method.

1. In a design review of a reclamation change, a reviewer asks: if we crash after page 0 of a chunk is on disk but page 1 is not, and the next chunk is then written starting at page 1, can reclamation later skip that chunk and reset the extent? Nobody can answer, and all reclamation unit tests pass.
2. A review of a compaction change asks what happens if reclamation runs on an extent after compaction wrote a new chunk there, but before compaction recorded it in the tree's metadata. The concurrent stress test passes on every CI run, and the reviewer approves after reading the code twice.
3. The interface between the LSM tree and the chunk store changed again this month.
4. The experts start by writing a model of the chunk store in Alloy and SPIN, and plan a tool that checks the Rust code against it. At a planning meeting someone asks who updates the model after the nine months end, and no engineer volunteers.
5. Pre-production load tests and the staggered-deployment dashboards show the node meets its latency and availability targets.

Tutor notes: 1 and 2 are the core ones: the bugs that matter are crash-state and interleaving cases that hand-written tests and code review do not reach. 3 shows only a constraint (the code keeps changing). The learner should come up with the strawman it kills: full proof-based verification, whose cost (3–10× the code, in safe background) must be paid again on every change. 4 shows one strawman being tried, an expert-owned model in a separate language (the authors' own first attempt), and the constraint that kills it: no owner after the experts leave. 5 is the distractor: performance and availability are covered and out of scope.
### Task
In 4–6 sentences: what fails, the root cause, the obvious fix someone would try first and why it fails, and which observations support this. Say which observation, if any, is unrelated.
### Hint
In observations 1 and 2 the tests pass and the reviewer still has no answer. What would you need in hand to answer such a question by machine instead of by reading code?
### Rubric
1. [P-cause] The bugs that matter are deep crash and interleaving cases, and nothing machine-checkable says what correct behavior is in those cases. Yes: says hand-written tests only check the scenarios someone thought of, so questions like 1 and 2 need a checkable definition of correct plus a way to reach those states. Partial: "test coverage is too low" or "write more tests for crashes and races" without saying why hand-written cases cannot keep up.
2. [P-strawman] The obvious fixes and why they fail: full proof-based verification (the learner's own) costs several times the code and cannot keep up with the rate of change (observation 3); an expert-written model in a separate language will have no owner after the experts leave (observation 4). Yes: names both fixes, each with why it fails. Partial: names one, or names a fix without the reason.
3. [P-signal] 1 and 2 are the same kind of problem (crash states and concurrency), and 5 is unrelated. Yes: groups 1 and 2 and sets aside 5 with a reason. Partial: does one of the two.
4. [P-goal] Automated checks of deep properties (functional, crash, concurrency) that are cheap enough to keep up with the code and are maintained by the engineers themselves; guarantees weaker than proof are acceptable. Yes: states the cost bound, who owns it, and that it may be weaker than proof. Partial: "find these bugs automatically" with no word on cost or ownership.
### Paper's answer
The node needs checks of deep properties (functional correctness, crash consistency, concurrency) that hand-written tests do not reach, on 44K lines of code that change all the time. Full verification costs several times the code, and the team cannot sustain it. A model written by experts in a separate language will not be kept in sync once the experts leave. The paper's problem: find a way to specify and check these properties that is automated, cheap enough to keep up with the code, and owned by the engineers. The authors accept weaker guarantees than proof to get this.
### Also tell
Crash consistency matters even though each shard is replicated across several nodes: a node that comes back wrong, or loses its whole disk, triggers large repair traffic and IO across the fleet, and sometimes needs an operator. The next brief starts from the problem statement above.
### Common gaps
- "Write more unit tests for these cases" → Observation 1 needs a page-boundary spill, a specific crash, and a later chunk at the same spot. How many such cases would you have to think of in advance?
- "Prove it anyway, just the core" → The core interface changed this month. Who updates the proof next month?
- Took performance or rollout as part of the problem → Is anything in observations 1 or 2 about speed?
- "Replication makes single-node crash bugs harmless" → What does a node that recovers into a wrong state cost the rest of the fleet?

## Exercise 2: Solution design — a spec the engineers keep alive
### Brief
The problem (from exercise 1): the node needs automated checks of functional correctness, crash consistency and concurrency that hand-written tests do not reach. Proofs are too costly, and an expert-written model in a separate language will lose its owner. The checks must keep up with the code and be maintained by engineers who do not know formal methods. Some facts about the code base:

1. Unit tests use mocks of each component. When an engineer changes a component's interface, the build fails until its mocks are updated too.
2. Ignoring disks, performance and crashes, each component behaves simply. For example, the LSM-tree index just maps a shard ID to its chunk locations.
3. Reclamation and compaction move data around on disk, but must never change what a get returns.
4. Every component can run against an in-memory disk inside an ordinary unit test.
5. The soft-updates code passes a write-order object into each disk append and gets one back. You can ask that object whether its operation has reached disk.

Tutor notes: 1 and 2 are the insight (engineers already keep mocks current; a trivial implementation of the interface can be both spec and mock). 3 lets background tasks be no-ops in the model. 4 makes running many generated sequences cheap; it is mostly neutral. 5 belongs to the crash check, which is in "also tell"; give credit under criterion 3 if the learner uses it.
### Task
Describe your design: (a) the one fact about the problem or workload it exploits, (b) the mechanism, (c) why it is correct, including the failure case that most threatens it, (d) what it costs and when that cost is bad.
### Hint
Think about what engineers already keep up to date without being asked, and why they do it.
### Rubric
1. [S-insight] Specs go stale when only experts own them; engineers already keep mocks current because the build breaks otherwise; so the spec should be something they must touch in normal work. Yes: links ownership of the spec to an artifact already in the engineers' workflow. Partial: "write the spec in Rust" or "keep it simple" without the ownership reason.
2. [S-mechanism] A per-component executable model in the same language, with the same interface and a trivial implementation, used as the unit-test mock; conformance is checked by generated random sequences of operations (API calls plus background tasks, which do nothing in the model) run on both, with outputs compared after each step. Yes: both the model-as-mock and the generated comparison, in any words. Partial: only one of the two, or hand-written tests against the model. One model of the node's public API instead of one per component also earns Yes.
3. [S-correct] Says what is compared after each step and names where plain equality is wrong: after a crash recent writes may legally be lost; overlapping calls have no "after"; an injected IO fault may fail only one of several IOs in a call. Yes: names at least one such case and a sound relaxation (for example: after a crash check only writes the system reports as durable, as in fact 5; for overlap, the result must equal some serial order; after an IO fault a get may return nothing but never wrong data). Partial: names the case but gives no relaxation, or a relaxation loose enough that wrong data passes.
4. [S-cost] It gives no guarantee: random search reaches only what the harness can reach. Yes: names a concrete way it misses bugs (a code path no sequence reaches, such as a cache miss with a large test cache; random keys that rarely repeat, so gets seldom hit) and a mitigation (coverage, bias toward earlier keys or page-size values, shrinking of long failing runs, which needs deterministic code). Partial: "it might miss bugs" with no case or mitigation.
### Paper's answer
The paper calls the approach lightweight formal methods, applied to ShardStore. Each component has a reference model: a trivial Rust implementation of the same interface (the LSM-tree index's model is a hash map). The models total 450 lines, 1% of the code, and they are the mocks in unit tests, so engineers must keep them current. The authors chose one model per component, not one for the whole node, because internal APIs make corner cases and fault paths easier to drive and failures easier to debug. Conformance (refinement) is checked by property-based testing: random sequences of API calls and background tasks (reclaim, clean reboot; no-ops in the model) run on the model and on the implementation over an in-memory disk, comparing outputs and the key-value map after each step. Arguments are biased only where there is evidence, such as sizes near the page size; biasing toward production traffic had no effect. Coverage shows blind spots. The code must be deterministic (even Rust's HashMap iteration order is random) so that failing runs shrink: bug #9 went from 61 operations to 6. Injected IO faults set a "has failed" flag: after a fault a get may return nothing, but never wrong data.
### Also tell
- Crash consistency: the soft-updates `Dependency` object that every mutating call returns is the crash spec. `DirtyReboot(RebootType)` is added to the operation alphabet; the reboot type chooses per component whether it flushes, and flush operations mixed into the sequence give partly flushed states. After a dirty reboot, anything whose `is_persistent()` is true must read back correctly (persistence); after a clean reboot, everything must be persistent (forward progress). This is not circular: persistence catches a dependency graph that is too weak, forward progress one that never completes. Listing every block-level crash state found no extra bugs and was much slower.
- Concurrency: linearizability against the same model. Loom checks small concurrency primitives exhaustively; Shuttle, a randomized checker the authors open-sourced, checks end-to-end harnesses that Loom cannot finish, at the cost of soundness.
- Also Miri for undefined behavior in unsafe Rust, and Crux to prove that deserializers cannot panic on any input up to a size bound.
- The next exercise needs the crash check.
### Common gaps
- Proposed a TLA+ or Alloy model checked by experts → Which test artifacts break the build when the code changes, so that engineers must fix them?
- Hand-written tests against the model → Who would have written down the scenario in observation 1 of exercise 1?
- Plain equality after a crash → Which writes may legally be gone after a crash, and who in the system already knows that?
- Biased inputs toward production traffic → The paper found it had no effect. What evidence should justify a bias?
- Took the crash spec from the write-order object → Is that circular? Which bug class does it never catch? (A dependency stronger than needed passes.)
- Trusted the model → Two of the 16 bugs found (#9, #15) were in the reference model itself. Who checks the spec?

## Exercise 3: Transfer — a journaled store
### Brief
ShardStore checks crash consistency with the `Dependency` objects that soft updates return for every operation: after a dirty reboot, whatever `is_persistent()` reports must read back. Another team wants to adopt the same reference models and property-based tests for its storage node. Their node uses a write-ahead log and fsync for crash consistency, and has no per-operation write-order objects.
### Task
Which assumption of the paper changes here? Does the insight still hold? What would you change, and what evidence would show that it works? In 5–8 sentences.
### Hint
After a crash, the model must know which writes are allowed to be gone. In a journaled store, what does the system know about what is on disk?
### Rubric
1. [T-assumption] The crash check assumes the implementation can say, per operation, whether it is durable; a WAL-plus-fsync store has no such object. Yes: names this assumption. Partial: "crash consistency works differently here" without naming what is lost.
2. [T-insight] The insight still holds: take the crash spec from what the implementation already knows about durability, now at a coarser grain (the last durable log position). Yes: says it holds and names a concrete source for the oracle. Partial: says it holds but names no source. Proposing to list every crash state or to teach the model the effect of each IO is No: those are the costly fixes the paper avoided.
3. [T-evidence] A concrete check. Yes: every operation acknowledged at or before the durable position must survive; later ones may vanish, but only as a suffix; recovery must yield a prefix of the log, which the model can replay and compare. Partial: only "acknowledged writes survive", with no prefix or suffix rule.
4. [T-evidence] Says what the coarser check misses and how to show the check works. Yes: names a bug class it cannot see, with a reason tied to the coarser grain, and proposes evidence (for example, replaying known crash bugs or seeding bugs and counting how many the check catches). Partial: "it is weaker" with no bug class, or evidence with no way to count misses.
### Paper's answer
The paper does not cover this case. A strong answer: expose the last durable log position as the oracle. Every operation acknowledged at or before it must survive a crash; later operations may vanish, but only as a suffix. Check that recovery yields a prefix of the log, and compare the recovered state with the reference model replaying that prefix. This keeps the paper's idea of taking the crash spec from the implementation's own durability tracking. It is a weaker, coarser spec than per-operation dependencies, and a good answer says which bugs it would miss.
### Also tell
- Two cases the paper leaves open: crashes during concurrent executions (no effective automated way found; the set of allowed recovered states grows fast) and resource exhaustion (no oracle, because real space leaks look like expected overhead from metadata, checksums and alignment). Either makes a good follow-up transfer.
- Results: 16 issues stopped before production (5 functional, 5 crash consistency, 6 concurrency). Validation code is about 20% of the implementation, against 3–10× for verified systems. 18% of harness lines were last edited by non-experts, and engineers asked to make the checks release blockers.
### Common gaps
- Enumerate all crash states instead → In the paper, block-level crash states found no extra bugs and were much slower. What would you gain here?
- "A journal makes crash consistency easy, so skip the check" → Who checks the recovery code that replays the log?
- No word on what is missed → Name one bug that passes your check. How would you know your check misses it?
