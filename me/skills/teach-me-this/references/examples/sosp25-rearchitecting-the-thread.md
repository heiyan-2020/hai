# Rearchitecting the Thread Model of In-Memory Key-Value Stores with μTPS
SOSP'25 · Youmin Chen, Jiwu Shu, Yanyan Shen, Linpeng Huang, Hong Mei / Shanghai Jiao Tong University, Tsinghua University · https://doi.org/10.1145/3731569.3764794
Paper type: new system / architecture (thread model; performance work driven by hardware counters)

## Dissection
- Background: RDMA/DPDK in-memory KV stores (MICA, FaRM) pin one thread per core, busy-poll the NIC, and run each request from start to finish in one function: poll, parse, index lookup, copy the value, reply. This is run-to-completion. At >10 Mops/s a request has a few hundred ns, while one cache miss costs 50–150 ns. The NIC writes packets straight into the LLC (Intel DDIO, two LLC ways). The older thread-per-stage model (SEDA; HBase has >10 stages and ~1000 threads) was dropped for fast hardware, because its OS-scheduled queues between stages cost too much.
- Problem: Run-to-completion puts steps with very different behavior into one thread on one core. Polling and replying touch a small network buffer and never conflict. Index traversal and value copy sweep a large memory area and, under skewed writes, need locks. So the large-footprint steps evict the network buffers (LLC miss rate 33%), and a thread that waits on a hot-item lock also stops polling and replying, so throughput falls as cores are added. Can the thread model itself be changed so that each kind of step keeps its own cache and its own scalability?
- Challenges: (1) Cache partitioning alone (CAT) does not fix it: DDIO writes in place into lines that already sit in any way, and one core runs both kinds of step, so both share one CAT mask. (2) Key-partitioned threads (share-nothing) remove locks but are badly imbalanced under skew, and skew is the common case in production. (3) Staged designs pay inter-core handoffs per request, and the classic many-stage, OS-scheduled version is far too slow at µs scale. (4) Hot items blur the line: under skew, part of the "large-footprint" work is actually small and cache-friendly. (5) The right number of threads per stage depends on item size, keyspace and skew, but in eRPC/FaRM-RPC the client chooses the server thread, so changing thread counts means telling every client; eRPC also allocates 15 MB of buffer per worker thread.
- Solution:
  1. Insight: the steps split cleanly by cache footprint, not by function. → Design: only two thread pools on separate cores. A cache-resident (CR) layer polls, parses, serves hot items and replies; a memory-resident (MR) layer holds the full index and data and does lookups and copies. Only CR cores touch the network buffers. With the two on different cores, CAT can give each its own ways. → Network buffers stay in cache; the motivation test (no handoff cost, deterministic replay) gives 1.22–1.54× and LLC miss 2% vs. 33% on the polling side.
  2. Insight: under skew, the hottest items are small enough to stay in cache too. → Design: a resizable hot set (count-min sketch + min-heap, ~10K items, sorted array for the tree index) served by the CR layer; the MR layer gets only misses and hides them with batched C++20 coroutines + prefetch. The hot set is kept small, because CR and MR differ by less than an order of magnitude (not DRAM vs. HDD), so a large hot set makes CR misses expensive. → Hot items stop being evicted; redirecting the hottest 0.1‰ of queries alone gives 1.08×.
  3. Insight: only index/data updates conflict; every other step scales. → Design: share-everything inside each layer, with per-item version + CAS lock bits (≤8 B updated atomically), and a thread count per layer chosen to limit how many threads contend. → A lock wait no longer stops polling and replying; no load imbalance from partitioning.
  4. Insight: with only two stages there is one handoff, and reconfiguration can stay on the server. → Design: CR-MR queue with one lock-free ring per thread pair, 16 B request descriptors, batched slots, completion piggybacked on the tail pointer, no value copy through the queue. Reconfigurable RPC: one shared receive queue (RDMA SRQ + multi-packet RQ); thread i takes slots with m mod n = i, so a new n is a server-side global variable; 64 KB response buffer per thread. An auto-tuner searches thread split (trisection, per cache size), cache size (linear probe, step 1K), and cache ways (separately, via PQOS), with a 10 ms monitoring window. → Handoff cost ~100 ns, amortized by batching; retuning takes 0.9 s and never blocks requests.
- Evidence: 28 cores, Xeon Gold 6330 (42 MB LLC), ConnectX-6 200 Gbps, 10M items. vs. BaseKV (identical except run-to-completion): 1.03–5.46×. Tree index YCSB-B/C 1.30×/1.29× on average; YCSB-B tree +19.71% at 8 B, +43.53% at 1 KB; tree 8 B +11.87–26.56%, hash 8 B +3.01–8.56% (except put-skew). Put-uniform 8 B only +3.01% (hash) / +11.8% (tree), due to coherence traffic on the receive buffer. Write-skew: BaseKV collapses at 64 B/256 B with hash index, normal at 8 B; share-nothing eRPC-KV is sometimes up to 12% faster than μTPS. Scan: +33.1%/+25.1% vs. BaseKV. ETC: +29.1/13.0/26.6% (10/50/90% get). Twitter: +44.5/39.8/0.1% (Cluster-12/19/31; 31 is uniform). Latency close to BaseKV (hash median slightly higher). Few cores: equal or slightly worse. Batching: +51.6% (tree), +93.7% (hash). Load change at 4 s, tuner starts 4.3 s, done 5.2 s, +20%.

Safe background (may be explained whenever asked): RDMA two-sided vs. one-sided verbs, busy polling, run-to-completion, LLC ways, DDIO, CAT, Intel PCM, share-nothing vs. share-everything, Zipfian/YCSB, MassTree, cuckoo hashing, optimistic version-number reads, coroutines and software prefetch, SEDA and HBase-style staging (only as the old design, never as the answer).

## Exercise 1: Problem finding — why does a fast KV server stop scaling?
### Brief
You run the server of an RDMA in-memory KV store. The server has 28 cores on one socket of a Xeon Gold 6330 (42 MB LLC) and a ConnectX-6 200 Gbps NIC; the NIC writes packets straight into the LLC with DDIO. Clients send two-sided RPCs. The store holds 10M items in MassTree (a cuckoo-hash build also exists). The thread model follows MICA/FaRM: each worker thread is pinned to a core, busy-polls for requests, and runs each request from start to finish. Any thread can serve any key. Values of 8 B or less are updated with one atomic instruction; larger values take a per-item CAS lock bit and a version number; reads are lock-free and check the version. Batching and prefetching are already on. The goal is well above 10 Mops/s. At that rate a request has a few hundred ns, and one DRAM miss costs 50–150 ns.

1. Intel PCM on the worker cores during a skewed read-heavy run shows an LLC miss rate of 33%. A stripped-down build that only polls the receive buffer, parses and replies (the receive buffer is smaller than the LLC) shows almost no LLC misses.
2. Tuning attempt: with CAT you keep all worker threads out of the two LLC ways that DDIO uses. Throughput stays about the same with small items and rises slightly with larger ones.
3. YCSB-A (50% get, 50% put), Zipfian keys, 256 B values, hash index: throughput goes down as you go from a few threads to 28, although half of the requests are gets that take no lock. With 8 B values the fall is gone.
4. The production traces you must serve are skewed: in the Twitter traces, a read-heavy cluster has Zipf alpha 0.74 and a write-heavy one 0.30.
5. In the 1 KB-value runs, the one-sided-RDMA B+-tree store you compare against (Sherman) looks very good. Its throughput there is limited mainly by the 200 Gbps link.

Tutor notes: 1 is the core cache clue: the request path as a whole misses a lot, its polling part alone does not. 2 is the failed cache fix; why it fails is a fact in exercise 2's brief. 3 is the contention clue: 8 B values use atomics, so locks are involved, and gets slow down too, so a lock wait stalls requests that never lock. 4 shows only the constraint (production is skewed). The learner should come up with the strawman it kills for the lock problem: partition keys across threads (share-nothing, as in eRPC-based stores), which removes locks but leaves some threads overloaded under skew. 5 is the distractor: link bandwidth matters only at 1 KB for a different design; the problem shows at small items, far below the link limit.
### Task
In 4–6 sentences: what fails, the root cause, the obvious fix someone would try first and why it fails, and which observations support this. Say which observation, if any, is unrelated.
### Hint
In observation 1, the polling part alone barely misses, but the full request path misses 33% of the time. What else runs on the same core between two polls?
### Rubric
1. [P-cause] Cache: the index walk and value copy (large footprint) evict the network buffers that polling and replying use, because they run on the same core. Yes: says which steps evict which, using the contrast in observation 1. Partial: "cache misses are high" or "the LLC is too small" without naming the steps.
2. [P-cause] Contention: a thread that waits on an update lock also stops polling and replying, so gets slow down too. Yes: explains why lock-free gets get slower (observation 3), in any words. Partial: "lock overhead" or "use a better lock" without explaining the gets.
3. [P-strawman] The obvious fixes and why they fail: cache partitioning (observation 2) and key partitioning (the learner's own; ruled out by the skew in observation 4), so the fix must be in the thread model. Yes: names both fixes, with skew as the reason key partitioning is ruled out. Partial: names only one, or names them without the reason.
4. [P-signal] Joins the two clues into one cause and sets aside the distractor. Yes: says both problems come from one thread running all steps on one core, and sets aside 5 with a reason (small items, far from 200 Gbps). Partial: does one of the two.
5. [P-goal] A goal a solution can be judged against. Yes: keep the small, conflict-free work in cache and scalable as cores are added, while any thread can still serve any key (no partitioning) and handoff costs stay small against a few hundred ns. Partial: "make it faster" or "fewer misses" with nothing that must be kept.
### Paper's answer
Run-to-completion puts every step of a request into one thread on one core, but the steps behave very differently. Polling, parsing and replying touch a small network buffer and never conflict. Index traversal and value copy sweep the index and data of 10M items and, under skewed writes, need locks. Run together, the large-footprint steps evict the network buffers (33% LLC miss), and a thread that waits on a hot-item lock also stops polling and replying, so throughput falls as cores are added. CAT does not help, and key partitioning removes the locks but is badly imbalanced under skew, which is what production sends. With a budget of a few hundred ns per request, a few misses already matter. The paper's problem: change the thread model so that each kind of step keeps its own cache and its own scalability.
### Also tell
Nothing extra. The next brief starts from this problem statement.
### Common gaps
- "Buy a CPU with a bigger LLC" → The index and values of 10M items still do not fit. Which data needs to stay in cache, and is it big?
- "The network is the bottleneck" → Observation 5 is a different design at 1 KB. At 8–256 B values, are you anywhere near 200 Gbps?
- "Partition keys to get rid of locks" → Under the skew in observation 4, how evenly would requests spread over the threads?
- "It's just lock overhead; use a better lock" → Gets take no lock and still slow down. Why would a lock on a put stop a get?
- Found only the cache half or only the lock half → Observations 1 and 3 have the same shape. What do the two steps that hurt each other have in common?

## Exercise 2: Solution design — keep the small work in cache and scalable
### Brief
The problem (from exercise 1): in run-to-completion, small-footprint, conflict-free steps (poll, parse, reply) and large-footprint, conflict-prone steps (index lookup, value copy) run in one thread on one core. The large steps evict the network buffers, and a lock wait stalls polling and replying. CAT and key partitioning do not fix it. Some facts about the setting:

1. CAT sets one cache-way mask per core. DDIO writes a packet into its two LLC ways only on a miss; if the buffer line already sits in another way (pulled in when a worker polled it), the NIC writes it there in place.
2. Passing a small message from one core to another costs about 100 ns, against a per-request budget of a few hundred ns.
3. The old staged server design, as in HBase, has more than 10 stages and about 1000 threads scheduled by the OS, whose scheduling latency is in ms.
4. Keys are Zipfian, so a small set of hot keys gets a large share of the requests.
5. In eRPC and FaRM-RPC, the client chooses which server thread handles its request.

Tutor notes: 1 is the insight's hardware fact: the fix needs the two kinds of access on different cores, and then CAT works. 2 says one handoff is affordable, many are not. 3 is why a per-function pipeline is the wrong answer. 4 and 5 are neutral here; they matter for the hot set and the reconfigurable RPC in "also tell".
### Task
Describe your design: (a) the one fact about the problem or workload it exploits, (b) the mechanism, (c) why it is correct, including the failure case that most threatens it, (d) what it costs and when that cost is bad.
### Hint
For each step of one request, write down how much memory it touches and whether two requests can conflict on it. Then ask where each step should run so that it never disturbs the others.
### Rubric
1. [S-insight] The steps split cleanly by cache footprint (and by whether they conflict), not by function, so that is where to cut. Yes: states that poll/parse/reply differ from index/copy in footprint and that this decides the cut. Partial: "separate networking from storage" without the footprint reason, or a cut by function into many stages.
2. [S-mechanism] Two pools on separate cores, with one handoff per request. Yes: one pool polls, parses and replies and is the only one that touches the network buffers; the other does index lookup and value copy; they run on different cores and pass requests through a cheap queue. Partial: more than two stages with no reason, or two pools without saying they must sit on different cores.
3. [S-mechanism] Contention is handled by limiting the threads that run the conflicting step, not by partitioning. Yes: any thread in a pool can serve any key (share-everything), the number of threads that do updates is kept small, and the polling threads never wait on a lock. A dedicated small set of threads for writes also earns Yes. Partial: "use fewer threads" without saying the polling side keeps serving; key partitioning earns No.
4. [S-correct] Why it removes the misses where CAT alone could not, and the case that threatens it. Yes: only small-pool cores touch the network buffers, so index walks on other cores cannot evict lines that DDIO writes in place, and per-core masks can now give each pool its own ways; plus one threat case, such as hot keys under skew being sent to the large pool, or uniform puts where the large pool reads the value from a buffer another core pulled into its cache. Partial: only one of the two.
5. [S-cost] The extra inter-core hop. Yes: names the handoff cost (latency, about 100 ns, amortized by batching) and one case where the split hurts or gains little, such as few cores (threads move in whole units), uniform write-heavy loads, or a split that is wrong for the current workload. Partial: "some overhead" with no case.
### Paper's answer
μTPS brings back thread-per-stage, but non-preemptive and with only two layers on separate cores. The cache-resident (CR) layer polls, parses, serves hot items and replies; it is the only one that touches the network buffers. The memory-resident (MR) layer holds the full index and data and does lookups and copies. Because no core runs both, index walks cannot evict the buffer lines DDIO writes in place, and CAT can give each layer its own ways. A quick test with the split but no handoff cost (deterministic replay, thread counts tuned by hand) gives 1.22–1.54×, and the LLC miss rate on the polling side drops from 33% to 2%, while the lookup side keeps about the same miss rate. Inside each layer the design is share-everything, with per-item version + CAS lock bits; the thread count per layer is chosen to limit how many threads contend, so a lock wait no longer stops polling and replying, and there is no imbalance from partitioning. The cost is one inter-core hop of about 100 ns, amortized by batching.
### Also tell
- Hot set: under skew the hottest items are small enough to stay in cache, so the CR layer serves a resizable hot set (count-min sketch + min-heap, ~10K items, sorted array for the tree index). Redirecting the hottest 0.1‰ of queries alone gives 1.08×. It stays small because CR and MR differ by less than 10× (not DRAM vs. HDD), so a big hot set makes CR misses costly. The MR layer gets only misses and hides them with batched C++20 coroutines + prefetch, which are no longer wasted on lines already in cache.
- CR-MR queue: one lock-free ring per thread pair, 16 B descriptors in batched slots, completion signaled by moving the tail pointer; values never go through the queue.
- Reconfigurable RPC: because the client picks the server thread in eRPC/FaRM-RPC (and eRPC uses 15 MB of buffer per thread), μTPS uses one shared receive queue (RDMA SRQ + multi-packet RQ); thread i takes slots with m mod n = i, so n changes on the server only. An auto-tuner picks the thread split, hot-set size and cache ways; retuning takes 0.9 s and never blocks requests.
- Limit: with uniform puts there is no hot set to exploit, and the CR layer pulls the receive buffer into its cache while parsing, so the MR layer reads the value from another core. The gain shrinks to a few percent.
- The next exercise uses these names, plus μTPS-H (libcuckoo) and μTPS-T (MassTree).
### Common gaps
- Stronger CAT masks, more prefetch or a smaller index inside the current model → One core runs both the polling and the index walk. Can that core give them two different masks?
- A pipeline with one pool per function (RPC, parse, index, copy, reply) → Each stage adds a hop of about 100 ns. What is the fewest stages that removes the interference, and what should decide the cut?
- Partitioned keys again to remove locks → Which step actually conflicts? Once it runs in its own pool, what can you control about it?
- Sent hot keys to the large pool → Under Zipf, how much memory do the hottest items take, and which pool fits that?
- No cost stated → On 3 cores, an ideal 2:5 split of threads is not possible. What happens to the gain?

## Exercise 3: Experiment design — convince a reviewer
### Brief
Problem: run-to-completion KV servers run every step of a request in one thread on one core. Small-footprint, conflict-free steps (poll, parse, reply) and large-footprint, conflict-prone steps (index, copy) interfere: buffers get evicted and lock waits stall the whole path. Method (μTPS): a non-preemptive thread-per-stage design with only two layers. The cache-resident layer polls, parses, serves a ~10K-item resizable hot set and replies, with its own cores and LLC ways. The memory-resident layer holds the full index and data and uses batched coroutines with prefetch. They talk through the CR-MR queue (per-pair rings, 16 B descriptors, batched). Reconfigurable RPC uses one shared receive queue so thread counts change on the server only, and an auto-tuner picks thread split, cache size and cache ways. Two stores: μTPS-H (libcuckoo) and μTPS-T (MassTree). The authors claim that changing only the thread model raises throughput over run-to-completion, with latency close to it, and that it handles skewed writes without partitioning keys.
### Task
List the 2–3 research questions the evaluation must answer. For the most important one, give the baselines, the workload, the metric, and the result that would refute the claim. For the others, one line each.
### Hint
The claim is about the thread model alone. What must the baseline share with μTPS so that nothing else could explain the gain?
### Rubric
1. [E-claim] Throughput against a baseline that differs only in the thread model, over a broad workload set. Yes: a run-to-completion build with the same code, same RPC, batching and prefetching on; workloads that vary mix, skew, item size and index (and ideally real traces). Partial: compares against MICA or FaRM directly (different RPC and index), turns off batching or prefetching in the baseline, or shows only skewed reads.
2. [E-cost] What the extra hop costs and where the gain vanishes. Yes: P50/P99 latency against throughput, plus at least one likely weak spot (uniform keys, write-heavy mixes, hash index, few cores). Partial: throughput only, or tests only at 28 cores on skewed reads.
3. [E-refute] Skewed writes, where contention could refute the claim. Yes: a thread sweep under skewed puts or YCSB-A with values above 8 B, against both the shared run-to-completion baseline and a share-nothing (key-partitioned) baseline. Partial: misses one of the three (sweep, values above 8 B, share-nothing baseline); 8 B values only, where atomics hide the lock problem, earns Partial at most.
4. [E-ablation] The contribution of the parts. Yes: at least two of batch size, the tuner under a workload that changes over time, the hot set, and the LLC ways, each varied alone. Partial: one ablation, or a fixed hand-tuned split presented as the system.
### Paper's answer
§5, on 28 cores, Xeon Gold 6330 (42 MB LLC), ConnectX-6 200 Gbps, 10M items. (1) Against BaseKV (same code, same RPC, batching and prefetching on, run-to-completion), plus eRPC-KV (share-nothing) and passive RDMA stores (RaceHash, Sherman), on YCSB A/B/C/E, 100% put/get skewed and uniform, 8 B–1 KB, tree and hash: 1.03–5.46× over BaseKV; tree YCSB-B/C 1.30×/1.29×; the gain grows with item size (YCSB-B tree +19.71% at 8 B, +43.53% at 1 KB); tree gains more than hash. Scan +33.1%/+25.1%; Meta ETC +29.1/13.0/26.6% (10/50/90% get); Twitter +44.5/39.8/0.1% (Cluster-12/19/31). (2) Latency (YCSB-A, 8 B, 2 to 64 client threads) is close to BaseKV, with a slightly higher hash median. Limits: put-uniform 8 B only +3.01% (hash) / +11.8% (tree), from coherence traffic on the receive buffer; Cluster-31 (uniform, 94% put) +0.1%; with few threads equal or slightly worse, because threads move in whole units (an ideal 2:5 split becomes 1:2 on 3 cores). (3) Under write skew BaseKV degrades at 64 B/256 B with hash index and is normal at 8 B; μTPS keeps scaling; eRPC-KV is sometimes up to 12% faster under write skew but much slower under read skew. (4) Batch size 1 to 20: +51.6% (tree), +93.7% (hash). Tuner: values switch 512 B → 8 B at 4 s, tuning runs 4.3–5.2 s, +20%, no downtime. Where it falls short: no separate ablation of the hot set or of CAT in the full system (and the tuner often gives almost all ways to the MR layer); idea 3 is shown only through end-to-end write-skew curves; no test with a much larger LLC or without DDIO/CAT; retuning takes 0.9 s, which is not tested against a hot set that shifts every second.
