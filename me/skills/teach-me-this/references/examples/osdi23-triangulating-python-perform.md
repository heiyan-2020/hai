# Triangulating Python Performance Issues with Scalene
OSDI'23 (Best Paper) · Emery D. Berger, Sam Stern, Juan Altmayer Pizzorno / UMass Amherst · https://www.usenix.org/conference/osdi23/presentation/berger
Paper type: tool (profiler) with a measurement-style evaluation

## Dissection
- Background: CPython is a bytecode interpreter written in C. Pure Python is 1–2 orders of magnitude slower than native code (pure-Python matrix multiply takes more than 60,000× as long as BLAS), and its objects are large (the integer 1 is 4 bytes in C, 28 in Python; "a" is 2 bytes vs. 50). So the main way to speed up Python is to find hot or memory-hungry pure-Python code and move it into native libraries (NumPy, scikit-learn, TensorFlow). Python profilers come in two kinds: tracing ones built on `sys.settrace` (cProfile, profile, yappi CPU, line_profiler, pprofile det., memory_profiler) and sampling ones (pprofile stat., py-spy, pyinstrument, Austin). Memory profilers measure RSS (memory_profiler, Austin) or intercept allocations and report the peak (Fil, Memray).
- Problem: To decide what to move to native code, a developer needs, per line, how much time and memory go to Python vs. native code, on unmodified programs, at an overhead low enough to run real workloads. No existing profiler gives that. Cheap sampling profilers record zero time for native code and child threads. Tracing profilers are slow (up to 36.8× median) and distort time spent in function calls. Memory profilers are either wrong (RSS) or slow and report only the peak.
- Challenges: (1) Timer sampling in CPython goes blind exactly where native code runs and in every thread but the main one. (2) The obvious accurate fix, tracing every call, line or allocation, costs 4× (tracemalloc) to over 150× (memory_profiler) and distorts what it measures. (3) The standard cheap memory fix, rate-based sampling (tcmalloc, Go, Java TLAB/JFR), samples by bytes allocated; Python's interpreter constantly creates and frees short-lived objects, so samples go to lines that churn the allocator, not lines that grow the footprint. (4) Native and Python memory must be told apart, though Python's own allocator calls into malloc.
- Solution:
  1. Insight: CPython handles a timer signal only when the interpreter loop regains control, and only in the main thread. In virtual (CPU) time, the only reason a signal arrives late is that native code was running. → Design: at each signal, measure elapsed CPU time T against the interval q; add q to the line's Python counter and T−q to its native counter. For threads: monkey-patch blocking calls (e.g. `threading.join`) to use timeouts of `sys.getswitchinterval()` so the main thread keeps waking; keep a sleeping/executing flag per thread; on each signal enumerate threads (`threading.enumerate`, `sys._current_frames`) and count a thread as native if its current bytecode is a call (`CALL_FUNCTION`, `CALL_METHOD`, `CALL` in 3.11). → Turns the cause of the blindness into the measurement, at sampling cost, with no tracing distortion.
  2. Insight: short-lived allocations and frees cancel out; what matters is change in footprint. → Design: a shim allocator interposed on both malloc/free (LD_PRELOAD / DYLD_INSERT_LIBRARIES) and Python's allocator (`PyMem_SetAllocator`), with a thread-local "inside allocator" flag to avoid double counting; take a sample only when |allocs − frees| crosses a threshold T (a prime slightly above 10 MB); record a timestamp and footprint at each crossing. → Few, deterministic samples that point at lines that change the footprint; Python vs. native memory per line; memory over time, not just the peak.
  3. Insight: a leak is an object allocated at a new peak that is never freed. → Design: at each new maximum footprint, track one sampled object; each free checks it with one pointer compare; keep (frees, mallocs) per site and compute a leak probability with Laplace's rule of succession; report when above 95% and overall memory growth slope is at least 1%. → Replaces tracemalloc (4× slowdown) plus manual snapshot diffs.
  Also: copy volume (MB/s copied per line) by interposing on memcpy, sampled by rate, since copies only ever add up; GPU utilization and memory read at each CPU sample.
- Evidence: 10 longest pyperformance benchmarks, median overhead 1.02× for CPU (and CPU+GPU) and 1.32× with memory on (worst: pprint 4.03×), vs. Memray 3.98×, Fil 2.71×, memory_profiler 37.11× (over 150× on three benchmarks), pprofile det. 36.83×. Function-call microbenchmark: a trace-based profiler reports 80% where the truth is 25%; Scalene is near the diagonal. 512 MB array: Scalene and Fil within 1%, Memray within 6%, RSS profilers far off. Threshold vs. rate sampling: median 18×, up to 676× fewer samples. mdp log: Scalene 32K, Austin 27 MB, Memray almost 100 MB. User case studies: NumPy code 125× faster (80 → 10,000 iterations/min), Pandas chained indexing 18×, Rich 45%, groupby 1.6 GB (43%) less memory, Semantic Scholar 92% lower cost.

Safe background (may be explained whenever asked): sampling vs. tracing profilers, `sys.settrace`, SIGPROF/`setitimer`, wall-clock vs. virtual (CPU) time, `time.process_time()`, RSS and demand paging, malloc interposition with LD_PRELOAD, the GIL, NumPy vectorization, the pyperformance suite, rate-based heap sampling in tcmalloc/Go/JFR in general (but not its bias under Python, and not when CPython runs signal handlers; that is part of exercise 2's brief).
Protected terms (not before the reveal of exercise N): Scalene, "threshold-based sampling", "copy volume", "leak score" (2); "triangulating", "function bias" (3).

## Exercise 1: Problem finding — why can't the group find the lines to fix?
### Brief
You are the performance person in a research group that writes most of its code in Python: data pipelines in Pandas, models in NumPy and PyTorch, a few long-running services. When something is slow or runs out of memory, people come to you and ask which lines to fix. The group wiki says pure-Python matrix multiply is over 60,000× slower than BLAS, and that the integer 1 takes 28 bytes in Python vs. 4 in C. You have a laptop-class 8-core machine and the usual Python profilers installed (cProfile, line_profiler, py-spy, pprofile, yappi, memory_profiler, Fil, Memray, Austin).

1. A grad student's gradient-descent classifier "already uses NumPy" and runs at 80 iterations per minute. They ask you, line by line, where rewriting will pay off.
2. You run pprofile in statistical (timer-sampling) mode on a script. The line `C = A @ B` on large arrays takes most of the run by wall-clock timing, but the profile shows no time on it.
3. In the same kind of profile, a function that runs in a `threading.Thread` worker also shows zero time.
4. The group's long-running services cannot be profiled with tracing tools on. Turning on tracemalloc alone slows apps down about 4×.
5. A colleague tried Intel VTune on a short script and got no Python data at all. The VTune docs say: "if your application has very low stack depth, which includes called functions and imported modules, the VTune Profiler does not collect Python data."

Tutor notes: 1 is the need: the decision is Python vs. native, so the answer must split each line that way, for time and for memory. 2 and 3 are the core: the cheap sampler is blind to native code and to threads, which is exactly where the student's time may be. Do not explain why it is blind; that is exercise 2. 4 shows the one strawman, "just trace everything", and the constraint that kills it (too slow for real workloads). 5 is the distractor: one tool's caveat, not the systematic problem.
### Task
In 4–6 sentences: what fails, the root cause, the obvious fix someone would try first and why it fails, and which observations support this. Say which observation, if any, is unrelated. End with the goal a new tool must meet.
### Hint
Start from observation 1. What exactly does the student need to know about each line to decide whether rewriting it will help?
### Rubric
1. [P-cause] The cheap sampler gives no time to lines in native code and in threads, so its per-line view is wrong exactly where the decision is made. Yes: names both native code and threads (2 and 3) as the blind spots, and says this is systematic, not one tool's bug. Partial: names only one of the two, or "pprofile is buggy, use another sampler".
2. [P-strawman] The obvious fix is to trace every call, line or allocation, and it fails: it is too slow for real workloads, so accuracy must come at sampling cost. Yes: names tracing as the fix and uses observation 4 to rule it out. Also Yes: says tracing distorts what it measures (each callback adds time to the call it measures). Partial: says tracing is slow but then proposes a faster tracer.
3. [P-signal] Total time per line is not enough, and VTune is unrelated. Yes: uses observation 1 to say the per-line answer must separate Python from native, and sets aside 5 with a reason (one tool's caveat; native profilers do not map time to Python lines anyway). Partial: does one of the two.
4. [P-goal] A goal a tool can be judged against. Yes: per line, CPU time and memory, each split into Python vs. native, including threads, on unmodified programs, at about the overhead of a sampling profiler. Partial: time only, no cost bound, or "a better profiler".
### Paper's answer
Python developers speed up code mainly by moving hot or memory-hungry pure-Python lines into native libraries. To choose those lines they need, per line, the time and memory spent in Python vs. in native code, including threads, on unmodified programs. Cheap timer-sampling profilers report zero time for native code and threads. Tracing profilers are 1.7–37× slower and distort call-heavy code. Memory profilers are either wrong (RSS-based ones such as memory_profiler and Austin) or 2.7–150× slower and report only the peak (Fil, Memray). The problem: get an accurate per-line Python/native split of CPU time and memory at about the overhead of sampling (§1).

### Common gaps
- "pprofile has a bug; use py-spy instead" → Suppose a sampler got total time per line right. Would the student then know whether a line is slow because of Python or because of the native call inside it?
- "Make tracing cheaper; write the callback in C" → cProfile already does that and is function-level only. Does a faster callback remove the time that each callback adds to the call it measures?
- "Use VTune or perf" → Native profilers see C frames. Does any of them tell you which Python line spent the time?

## Exercise 2: Solution design — see native time and memory at sampling cost
### Brief
The problem (from exercise 1): to choose which lines to move to native code, developers need, per line, CPU time and memory split into Python vs. native code, including threads, on unmodified programs, at about the overhead of a sampling profiler. Cheap timer samplers show zero for native code and threads; tracing is slow and distorts. Some facts about CPython and the setting:

1. CPython runs a Python-level signal handler only in the main thread, and only when the interpreter loop gets control back (it checks after some bytecodes, such as jumps). A long native call such as `A @ B` holds a pending signal until it returns.
2. A timer can be set to fire after an interval of wall-clock time or of the process's CPU time (`setitimer`); `time.process_time()` reads CPU time.
3. From the main thread, `threading.enumerate()` and `sys._current_frames()` show every thread's current frame and bytecode. A thread running Python code moves on to its next bytecode almost at once.
4. Heap profilers in tcmalloc, Go and Java JFR take one sample per N bytes allocated. The Python interpreter creates and frees huge numbers of short-lived objects.
5. Native libraries call malloc directly. Python's own object allocator can be replaced with `PyMem_SetAllocator`, and it gets its memory from malloc. malloc can be interposed with LD_PRELOAD.

Tutor notes: 1 and 2 are the CPU insight: the signal is late by the native time, and in CPU time nothing else (I/O, waiting) can make it late. 3 is what the thread mechanism needs. 4 is the memory insight (rate-based sampling lands on churn) mixed with a tempting wrong path. 5 is neutral setup, but it hides the double-counting trap.
### Task
Describe your design, for both CPU time and memory: (a) the fact about the problem or workload each part exploits, (b) the mechanism, (c) why it is correct, including the failure case that most threatens it, (d) what it costs and when that cost is bad. About 10–15 sentences.
### Hint
Fact 1 describes a limit of CPython. Ask whether that limit only destroys information, or whether it carries some.
### Rubric
1. [S-insight] For CPU: a late signal carries information. Measured in CPU time, the delay can only come from native code, so the delay is the native time. Yes: says the delay measures native time and why the clock must be CPU time (wall-clock delay could be I/O or waiting). Partial: "measure the delay" with wall-clock time or with no argument for the clock.
2. [S-mechanism] Per-line charging, and threads. Yes: with interval q and elapsed CPU time T, charge q to the current line's Python counter and T−q to its native counter; and a concrete way to cover other threads (make blocking calls such as `join` time out so the main thread keeps waking; at each signal read each thread's current bytecode: a call bytecode means native, else Python; skip sleeping threads). Partial: the split without threads, or threads with no concrete way to wake the main thread or to classify a thread.
3. [S-insight] For memory: sample on the net change in footprint, not on bytes allocated, because short-lived objects cancel out. Yes: says rate-based sampling sends samples to lines that churn, not lines that grow memory, and proposes a trigger on |allocs − frees| (any threshold). Also Yes: says the samples should carry time so the tool shows memory over time, not only the peak, if it also gets the trigger right. Partial: "sample allocations" with a per-byte or unspecified trigger, or recording every allocation.
4. [S-correct] The Python/native memory split needs both allocators intercepted without counting bytes twice. Yes: hooks both malloc and Python's allocator, and avoids double counting when Python's allocator calls malloc (for example a thread-local "inside allocator" flag that just forwards). Partial: hooks only one, or both with no answer for double counting.
5. [S-cost] Where the design gives wrong or empty results. Yes: names at least one concrete case, such as: a threshold around 10 MB misses a program with a 5 MB footprint or a leak of 1 MB an hour; a flat footprint with heavy churn shows nothing in the memory profile; a BLAS call that uses all 8 cores grows CPU time up to 8× the wall time, so the native share is in core-seconds; blocking calls must be patched. Partial: "some overhead" with no case.
### Paper's answer
Scalene. CPU: a timer fires every q of CPU (virtual) time. CPython runs the handler only when the interpreter regains control, so in CPU time the only reason it runs late is native code. With elapsed CPU time T, the handler charges q to the current line's Python counter and T−q to its native counter. This has sampling cost and no tracing distortion. Threads: Scalene monkey-patches blocking calls such as `threading.join` to use timeouts of `sys.getswitchinterval()`, so the main thread keeps waking. At each signal it enumerates threads; a thread whose current bytecode is a call (`CALL_FUNCTION`, `CALL_METHOD`, `CALL` in 3.11) counts as native, and a per-thread flag skips sleeping threads. Memory: a shim allocator sits on both malloc/free (LD_PRELOAD / DYLD_INSERT_LIBRARIES) and Python's allocator (`PyMem_SetAllocator`), with a thread-local flag against double counting. "Threshold-based sampling" takes a sample only when |allocs − frees| crosses a prime slightly above 10 MB, and stores a timestamp and footprint, which gives a memory timeline instead of a peak.
### Also tell
- Leaks: at each new peak footprint, Scalene tracks one sampled object; each free checks it with one pointer compare. Per site it keeps (frees, mallocs) and computes a leak probability ("leak score") with Laplace's rule of succession, and reports above 95% when memory keeps growing (slope at least 1%). This replaces tracemalloc (4×) plus manual snapshot diffs.
- "Copy volume": MB/s copied per line, by interposing on memcpy and sampling by rate, which is fine here because copies only ever add up (it catches hidden copies such as a Pandas `concat` that doubles memory).
- GPU utilization and memory are read at each CPU sample.
- The next exercise uses these names.
### Common gaps
- Kept tracing, but selective or in C → Each callback adds time to the call it measures. How does your design avoid both the cost and that distortion?
- Sampled stacks from outside the process, like py-spy or Austin → What does a sample need to know beyond "which line is on the stack"?
- Measured the signal delay in wall-clock time → A line waits 2 s on a socket. What does your rule charge to native code?
- Ignored threads → The main thread is blocked in `join` while a worker runs. Which handler runs, and when?
- Rate-based memory sampling → Which lines collect the samples, and do those lines grow the footprint? Is the result the same from run to run?
- Reported the peak only → A program allocates and frees a 4 GB object, then allocates a 4 GB + 8 byte one. What does a peak report show, and would deleting that object lower the peak much?
- Hooked both allocators without a guard → Python's allocator calls malloc. How many times does your shim count those bytes?

## Exercise 3: Experiment design — convince a reviewer
### Brief
Problem: Python developers need a per-line split of CPU time and memory into Python vs. native code, at low overhead, and no profiler gives it. Method (Scalene): CPU sampling in virtual time, where the delay of each signal beyond the interval q is charged to native code; threads are handled by timeouts on blocking calls and a check of each thread's current bytecode. Memory: a shim on both malloc and Python's allocator, sampled whenever the net change in footprint crosses ~10 MB ("threshold-based sampling"), with timestamps for a memory timeline. On top: leak detection at new peaks, copy volume from memcpy, GPU utilization and memory. The authors claim accurate CPU and memory profiles, with the Python/native split, at about the overhead of sampling profilers, where other profilers are slow or wrong.
### Task
List the 2–3 research questions the evaluation must answer. For the most important one, give the baselines, the workload, the metric, and the result that would refute the claim. For the others, one line each.
### Hint
The design rejects tracing for two reasons and RSS for one. Which experiment shows each reason, against a ground truth you know by construction?
### Rubric
1. [E-claim] Accuracy against a known ground truth where other tools fail. Yes: a CPU test whose true answer is known by construction (for example two equivalent loops, one calling a helper, one inlined, timed with high-resolution timers, varying the share) and a memory test of known size where RSS fails (for example allocate one large array and touch only part of it), each run against all the profilers. Partial: compares profilers with each other and no ground truth, or tests only pure-Python code, or touches the whole array.
2. [E-cost] Overhead on many real programs, memory on and off, with the worst case. Yes: a suite of long-running benchmarks, CPU-only and full modes compared with like modes of other tools, and the worst case reported as well as the median. Partial: median only, short runs where startup dominates, or the full mode compared with CPU-only modes of others.
3. [E-ablation] Threshold vs. rate-based sampling. Yes: same programs under both policies, counting samples or log size, and checking that attribution stays right or that overhead drops because of it. Partial: sample counts only.
4. [E-refute] The Python/native split itself, on the workloads the design targets. Yes: a test with a known native share (for example a C call of known length inside a Python loop), or native-heavy and multi-threaded workloads, with the result that would refute the claim. Partial: mentions native-heavy or threaded workloads but gives no ground truth.
### Paper's answer
§6. (1) CPU accuracy: in the call vs. inlined microbenchmark, trace-based profilers are far off the diagonal (worst: 80% reported for 25% actual, the "function bias"); Scalene is close. (2) Memory accuracy: one 512 MB array, touched 0–100%. Scalene and Fil are within 1%, Memray within 6%, memory_profiler and Austin (RSS) far off. (3) Overhead: the ten longest pyperformance benchmarks, each looped past 10 s, interquartile mean of 10 runs, 8-core Ryzen 7, CPython 3.10.9. Median: Scalene CPU 1.02×, CPU+GPU 1.02×, full 1.32× (worst pprint 4.03×); py-spy 1.02×, Fil 2.71×, Memray 3.98×, pprofile det. 36.83×, memory_profiler 37.11×. (4) Threshold vs. rate sampling: 2× to 676× fewer samples (median 18×); log size on mdp: Scalene 32K, Austin 27 MB, Memray almost 100 MB. Where it falls short: no controlled test of the Python/native split itself; the benchmarks are mostly pure Python, not the native-heavy, multi-threaded code the design is built for; sample counts are shown, but not that attribution stays right or that overhead drops because of them; leak detection and GPU profiling are not evaluated; the overhead summary differs across sections (intro 0%/32%, §6.4 2%/30%, Table 3 1.02×/1.32×).
### Also tell
External case studies: NumPy code 125× faster (the classifier went from 80 to 10,000 iterations per minute), Pandas chained indexing 18×, Rich 45%, a groupby 1.6 GB (43%) less memory, Semantic Scholar 92% lower cost. They are self-reported: evidence of use, not controlled results.
### Common gaps
- No ground truth → If two profilers disagree on a line, how do you know which one is right?
- Median overhead only → What does the median hide? Which benchmark would you show a skeptical reviewer?
- Did not test the split → How would you build a program whose native share you know in advance?
- No edge cases for the threshold → What does Scalene report for a program whose whole footprint is 5 MB, or one that leaks 1 MB an hour?
- Took the claimed extras on trust → Leak detection and GPU profiling are claimed. What is the minimum experiment for each, and what metric (for leaks: precision and recall)?
